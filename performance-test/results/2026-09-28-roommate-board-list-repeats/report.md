# RoommateBoardListGetTest 반복 부하 측정

- 측정일: 2026-09-28 (Asia/Seoul)
- 대상: 실행 중인 로컬 백엔드, H2 시드 설정 `seed.load-test.records-per-entity=1000`; 측정 전후 게시물 목록 `totalElements=1002`, 종료 후 health `UP`
- nGrinder: `RoommateBoardListGetTest.groovy` 리비전 34, 1 Agent·1 process, VUser당 100회, ramp-up 없음, 샘플링 간격 2초, `connectionReset=false`
- 순서: 1 VUser 20회 워밍업(ID 259) → 각 회차의 1→5→10 VUser, 회차 사이 60초 대기. 단계 사이 30초 대기. 테스트는 서로 겹치지 않았다.
- 오류가 난 단계에서 상위 VUser로 올라가지 않는 실행기 정책에 따라 각 회차의 10 VUser는 실행하지 않았다. 5 VUser 오류가 세 번 모두 재현되어 12~15 VUser 탐색도 진행하지 않았다.

Prometheus의 백엔드 지표(5초 수집)와 해당 테스트에 배정된 `apm-ngrinder-agent-1`의 Docker 통계(약 15초 간격)를 테스트 시작·종료 시각으로 잘라 분석했다. 아래 CPU 값은 각 테스트 구간의 관측 최대값이다.

5 VUser 구간의 서버 지연과 CPU 상승은 관찰되지만, 현재 자료만으로 H2·쿼리·JVM·호스트 자원 중 원인을 특정할 수 없다. 첫 회차에서 Hikari 대기가 최대 2개 관찰됐고, 다른 두 회차에서는 0개였다. 이전 탐색의 15~20 VUser Agent 로그에는 5초 클라이언트 타임아웃이 있었다. **이번 실행의 Agent 오류 스택은 확보하지 못했으므로** 이번 오류도 같은 예외라고 단정하지 않는다.

표의 p95는 nGrinder가 제공하는 **2초 구간별 평균 응답시간**의 p95다. 개별 요청 응답시간의 p95/p99는 현재 CSV와 Prometheus 설정에서 복원할 수 없다. 오류 요청이 평균 응답시간에 어떻게 반영되는지도 개별 요청 로그 없이는 검증할 수 없다. 따라서 이 표의 평균과 p95로 사용자 체감 지연의 상한을 판단하지 않는다.

## 판단과 다음 측정

현재 환경에서는 1 VUser만 오류 없이 반복됐고, 5 VUser는 세 번 모두 실패했다. **1,000건 시드에서 5 VUser를 안전한 부하 수준으로 취급하거나 10 VUser 이상의 한계를 추정할 수 없다.** 다른 13개 스크립트로 같은 부하 단계를 확장하기 전에, 이전 측정과 1 VUser 지연이 약 3배 차이 나는 이유를 확인해야 한다. 서버 실행 옵션·호스트 CPU 점유·쿼리 및 H2 처리 시간을 같은 조건으로 기록한 후 1→3→5 VUser를 반복하는 것이 다음 단계다. 응답시간 분포가 필요하면 개별 요청의 측정값을 수집하거나 서버 히스토그램을 활성화해야 한다.
