# 조회 스크립트 순차 실행 및 H2 시드 크기 선정

2026-09-28에 [run-read-sequential.ps1](../../tools/run-read-sequential.ps1)로 nGrinder의 조회 스크립트 14개를 1 Agent·1 process·1 thread(1 VUser)에서 순차 실행했다. 각 스크립트의 테스트가 완료된 뒤 다음 테스트를 시작했다. 앞선 단일 실행 검증에서 실패한 채팅방 상세와 하우스룰 상세는 fixture를 수정하기 전까지 제외했다.

## 실행 결과

| `records-per-entity` | 실제 게시글 수 | 전체 스크립트 | 게시글 목록 평균 | 추천 목록 평균 |
|---:|---:|---:|---:|---:|
| 500 | 502 | 14/14 통과, 각 3회 요청 | 260ms | 235ms |
| 1,000 | 1,002 | 14/14 통과, 각 3회 요청 | 533ms | 557ms |
| 1,250 | 1,252 | 14/14 통과, 각 3회 요청 | 459ms | 874ms |

500건에서는 앞서 각 5회 요청으로도 14개가 모두 통과했다. 게시글 목록 평균은 205ms, 추천 목록 평균은 230ms였다. 원본 실행 결과: [500건·3회](./read-sequential-20260928-190554.json), [500건·5회](./read-sequential-20260928-190109.json), [1,000건·3회](./read-sequential-20260928-191109.json), [1,250건·3회](./read-sequential-20260928-191519.json).

두 500건 실행은 서버 종료 방식의 문제로 다음 시드 크기 전환 전에 멈췄다. 각 500건의 14개 테스트 결과는 완료됐으며, 이후 JDK 실행 파일을 직접 사용하도록 수정했다. 마지막 두 목록의 1,000→1,250건 반복 실행에서 서버 전환과 종료가 정상 작동하는 것을 확인했다.

목록 두 개는 크기별 변동을 확인하려고 1,000건과 1,250건에서 **각 10회 요청을 3번 반복**했다. 12개 테스트 모두 오류 0건이었다.

| 시드 크기 | 게시글 목록: 반복별 평균 / 3회 평균 | 추천 목록: 반복별 평균 / 3회 평균 |
|---:|---|---|
| 1,000 | 488 / 495 / 458ms → **480ms** | 524 / 309 / 322ms → **385ms** |
| 1,250 | 807 / 724 / 690ms → **740ms** | 780 / 722 / 757ms → **753ms** |

[반복 측정 원본 JSON](./read-sequential-20260928-191914.json)에 실행 ID, 요청 수, 오류 수, nGrinder 평균 응답시간과 스크립트 리비전이 있다.

## 권장 크기

**현재 H2 기반의 조회 API 탐색 시험은 `seed.load-test.records-per-entity=1000`을 임시 기준으로 사용한다.** 500건은 빠른 계약 확인에 쓰고, 1,250건은 데이터 증가에 따른 지연을 보는 비교군으로 유지한다. 1,000건에서 14개 조회 스크립트가 모두 성공했고, 반복 측정에서 두 비용이 큰 목록 API의 평균이 대략 0.4~0.5초였다. 1,250건에서는 두 목록 모두 약 0.75초로 증가했다.

이 숫자는 운영용 시드의 확정값이나 처리 용량이 아니다. 각 반복의 요청 수가 10건이어서 p95/p99를 신뢰성 있게 추정할 수 없고, VUser가 1명이라 동시 처리 병목도 아직 확인하지 않았다. 관리형 서버는 `spring.jpa.show-sql=false`로 실행했으므로 이전의 스크립트 검증 로그에서 측정한 경과시간과 직접 비교하지 않는다. 현재 시드 설정은 게시글뿐 아니라 다수의 엔터티와 메타 데이터도 같은 수로 늘린다. 실제 용량 시험에서는 PostgreSQL과 엔터티별로 정한 데이터 규모·분포로 다시 측정한다.

## 재실행

```powershell
$env:NGRINDER_PASSWORD = '<controller password>'
./performance-test/tools/run-read-sequential.ps1 -BackendProject C:/dev/workspace/KnockIn/back/11th-1team-BE -SeedSizes 500,1000,1250 -Repetitions 3 -IterationsPerRun 10
```

이 명령은 백엔드 JAR을 빌드하고 시드 크기별로 서버를 기동·종료한다. 이미 빌드한 JAR을 사용할 때는 `-JarPath`를 지정한다. 기존 서버에서 검증만 할 때는 `-SeedSizes`를 생략한다. 새 실행 결과는 기본적으로 `performance-test/results/YYYY-MM-DD-read-sequential/`에 고유 시간 이름의 CSV·JSON·Markdown 파일로 저장된다. `-OutputDirectory`로 저장 위치를 바꿀 수 있다. nGrinder Controller의 비밀번호는 파일에 저장하지 않는다.

이번 환경에서는 Gradle 의존성 다운로드에 네트워크 권한이 필요해 JAR을 먼저 빌드하고 `-JarPath C:/dev/workspace/KnockIn/back/11th-1team-BE/build/libs/KnockIn-0.0.1-SNAPSHOT.jar`로 실행했다. 코드 변경 뒤 기존 JAR을 재사용하면 변경 내용이 반영되지 않으므로 다시 빌드해야 한다. 최종 스크립트는 10건 시드·스크립트 1개로 기동, 1회 요청, 결과 기록, 서버 종료까지 재검증했다.
