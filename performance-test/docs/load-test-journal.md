# 조회 API 부하 테스트 작업 일지

## 2026-09-28 · 현재까지

### 1. 시드 데이터 크기를 먼저 탐색

H2의 `seed.load-test.records-per-entity`를 늘리며 조회 테스트를 실행했다. 초기 단일 실행에서는 1,000건일 때 약 1~2초, 2,000건일 때 약 6초대, 10,000건에서는 30초 이상이 걸렸다. 이는 nGrinder의 **전체 실행 경과시간**이므로 개별 API 응답시간과 구분해야 한다. 시드 크기가 성능에 큰 영향을 준다는 문제를 확인했다.

### 2. 반복 실행 자동화와 임시 기준 선정

서버 재기동, nGrinder UI 실행, 결과 복사를 반복하기 어려워 Codex 에이전트와 nGrinder REST API를 활용했다. 16개 조회 시나리오 중 14개가 정상 동작했고, 실패한 2개는 테스트 fixture 문제로 분리했다. 시드별 서버 기동·종료와 14개 스크립트 순차 실행을 자동화했으며, 이후 다른 API에도 쓸 수 있는 Bash 실행기를 만들었다.

500·1,000·1,250건을 비교하고, **1,000건을 현재 H2 탐색용 임시 기준**으로 정했다. 1,000건에서 14개 조회 스크립트가 모두 통과했고, 게시물 목록과 추천 목록의 반복 평균은 각각 약 480ms·385ms였다. 1,250건에서는 둘 다 약 750ms로 증가했다.

### 3. 게시물 목록 조회에서 낮은 처리량 확인

`RoommateBoardListGetTest`를 먼저 1→5→10 VUser로 늘렸다. 5 VUser에서 TPS 4.18, 10 VUser에서 TPS 4.04로 처리량이 늘지 않은 반면 평균 응답시간은 약 1.2초→2.5초로 증가했다. 15 VUser부터 오류가 발생했다.

같은 1,000건 시드로 3회 반복하자 이전과 달리 1 VUser 평균부터 **1.33~1.75초**로 느려졌다(앞선 측정은 496ms). 5 VUser는 세 번 모두 오류가 발생해 10 VUser 이상은 진행하지 않았다. 동일한 시드 크기만으로 결과가 재현되지는 않았다.

### 4. 환경 문제를 인지하고 우선순위 조정

한 기기에서 서버·nGrinder를 실행하면서 다른 작업도 수행했다. 반복 측정 중 시스템 CPU 사용률은 최대 약 98%였고, 실행별 응답시간과 오류 수가 달랐다. **현재 TPS를 애플리케이션의 확정 성능 한계로 해석할 수 없다.**

나머지 13개 API로 부하 테스트를 확대하기 전에 중요한 API인 **게시물 목록 조회**부터 확인한다. 다음에는 서버 실행 조건과 호스트 자원 사용을 고정하고, 쿼리·H2 처리 시간과 오류 원인을 살핀 뒤 1→3→5 VUser로 재측정한다. 그 결과를 바탕으로 조회 로직을 튜닝할 계획이다.

**배운 점:** 자동화는 반복 측정을 가능하게 했지만, 숫자를 비교하려면 측정 환경의 재현성과 오류 원인 확인이 먼저다.


## 2026-09-30 · 목록·검색 실제 계약 smoke

산출물을 APM으로 통합한 뒤 현재 소스를 빌드하고 H2 seed1000·SQL 로그 비활성화 시험 서버에서 네 조건을 확인했다. Controller 289~292는 각각 1 VU·3회 성공, 오류/CSV 누락 0건이다. 기본 익명·인증 및 익명 검색은 이력이 증가하지 않았고, 인증 검색은 3건 증가했다. Agent 환경 변경 없이 토큰을 제공할 수 있도록 JSON `tokenFile` 경로 대체 설정을 추가했다. 토큰을 정리하고 시험 서버를 종료한다.

이번 실행은 정상 응답·이력 저장·측정 파일 배포/수집 확인이다. 성능 기준선·전후 개선률로 해석하지 않는다. 다음은 나머지 프로필 fixture 검증과 고정 조건의 워밍업/1→3→5 VU 반복 측정이다. [상세 결과](../results/2026-09-30-roommate-board-list-smoke/report.md).


## 2026-09-30 · 필터·페이지 검증과 반복 기준선

DB 기반 기대 count를 채워 17개 프로필을 각각 3회 검증했다. 차단 관계로 기존 관심 fixture가 모두 제외되는 문제는 전용 H2에 정상 관계 한 건을 준비하고 토큰 회원을 분리해 해결했다. 주 경로의 별도 워밍업 후 1→3→5 VU에서 회당 100요청/VU·3반복을 계획해 측정했다. 최초 3 VU는 helper의 출력 폴더 동시 생성 경쟁 조건으로 중단됐고, `Files.createDirectories`로 수정해 3 worker 회귀 검증 후 재개했다. 실패 실행 318은 정상 기준선에서 제외하고 로그 원본을 보존했다.

[반복별 결과·CPU/GC/Hikari·표본·검색 저장 증분](../results/2026-09-30-roommate-board-baseline/report.md)에 실행 완료 범위와 한계를 기록했다. SQL/실행계획 진단과 익명 검색·인증 기본 조회 대조군의 동일 부하 측정이 다음 단계다. 애플리케이션 성능 최적화는 아직 수행하지 않았다.


## 2026-09-30~10-01 · 네 경로 장시간 대조와 병목 확인

익명/인증 × 검색어 유무 네 경로를1VU·3반복으로 측정했다. 각100건 워밍업과 최소180초 실제 표본을 확보하고 동일140초 구간을 비교했다.12회174,285건 중 성공174,280건·전송 오류5건, 인증 검색 이력3,081건 증가를 확인했다. 오류 있는 실행도 결과에 포함했다. 시간 종료·GET 묶음 우회는 집계 불일치로 제외하고, Controller 반복 상한을 일시 높이는 방식으로 기존 요청별 실행을 유지한 뒤 원상 복원했다.

동일 구간 p95 중앙값은 익명 기본11.086ms, 인증 기본245.952ms, 익명 검색9.377ms, 인증 검색244.009ms다. 실패 실행의 서버 완료 counter와 클라이언트 성공 수를 대조했고, 측정 시간대의 Tcpip4227/4231은 관측되지 않았다. 전송 뿌리 원인은 아직 확정하지 못했다. 공유 호스트 반복 편차와 전송 오류를 숨겨 오류 없는 기준선·운영 수용량으로 판정하지 않았다.

부하 종료 후 SQL10회/경로와 실제 바인딩 SELECT 계획25개를 수집했다. 동적 메타 통계의 캐시 문제는 고유 SELECT 주석과 content/count 실행 횟수 검증으로 해결했고 첫 통계 시도는 제외 자료로 보존했다. 인증 content/count가 DB 실행 시간의99.98% 이상을 차지하고 BLOCK 전체 스캔을 확인했다. 두 NOT EXISTS 후보의4쿼리 형태·4회원 결과16비교가 같았고 SQL 실행 시간95.58~98.55% 감소를 관측했다. 백엔드/JAR/인덱스는 변경하지 않아 API 개선률은 아직 미측정이다.

다음은 `notBlockedBetween`의 방향별 NOT EXISTS 구현·양방향/삭제 차단과17프로필 계약 검증·동일 snapshot/측정기 전후 재측정이다. 이번 스크립트 snapshot을 선택할 옵션을 추가했고, 향후 전송 오류 진단을 위해 예외 메시지 없이 뿌리 클래스만 남기는 CSV schema2를 보강했다. 실제 Agent 라이브러리 오프라인 smoke와 Python4개 테스트를 통과했다. Controller 설정·SQL logger/통계를 복원하고 모든 임시 토큰과 직접 기동 서버를 정리했다.
